# Developing ceproof

**Build & test:** `npm install`, then `npm run build` to compile TypeScript to `dist/`, or `npm test` to run the vitest suite directly against `src/` (no build needed for tests). `npm run dev -- scan <path>` runs the CLI without building, via `tsx`.

**Public mirror and `tests/private/`:** `scripts/publish-mirror.sh` builds the public source mirror and (correctly) excludes the private key-generation tooling under `scripts/keygen/`. Any test that reaches that tooling therefore cannot run in the mirror — a static import fails `tsc -p tsconfig.test.json` with TS2307, and the child-process trick two of them use fails later at runtime with `ERR_MODULE_NOT_FOUND` — so those tests live under `tests/private/`, which the same script excludes. They are not skipped or weakened here: they run unconditionally in this repo. `npm run test:public-tree` is the gate: it builds the mirror's exact file selection (reusing that script's own `EXCLUDE_RE`) into a throwaway sibling directory and runs the real `npm test` inside it. Run it after touching anything under `tests/`, `scripts/` or the exclusion list. Nothing is written inside this repo and nothing is pushed.

**Project shape:** `src/ecosystems/npm/*Parser.ts` are pure functions — `(fileContents, options) → { packages, warnings }` — with no filesystem access, which is what makes them trivial to test against fixtures. `src/ecosystems/npm.ts` is the only module that touches disk: it picks a lockfile by priority (package-lock.json > pnpm-lock.yaml > yarn.lock), calls the matching pure parser, then does the filesystem-dependent work parsers structurally can't (checking whether an optional/peer dependency is actually installed under `node_modules`, detecting monorepo workspaces, falling back when no lockfile exists).

**Adding a fixture:** create a new directory under `fixtures/`, add a `package.json` and the lockfile you're testing (plus a real `node_modules/<pkg>/package.json` if the test needs to verify on-disk presence, e.g. for optional-dependency filtering). Point a new `it(...)` block in the matching `tests/ecosystems/npm/*.test.ts` file at it by directory name — fixtures are read via `fs.readFileSync`, no registration step needed.

**Before a release:** `npm test`, `npm run test:public-tree`, then `bash scripts/verify-pack.sh`, and re-run the latter whenever anything under `data/`, `scripts/` or `package.json`'s `files` array changed — a stale pass is worse than no check (see the doctrine note in CLAUDE.md for the packaging bug that rule came from). `verify-pack.sh`'s own header comment carries the one known flake in that gate (a one-in-seven `data/eol-snapshot.json missing after install`, suspected npm cache), what to check if it recurs, and when to treat it as a real packaging bug rather than noise. The per-version command sheets (`distribution/RELEASE-<version>-COMMANDS.md`, kept outside this repo at the portfolio level) are the record of a specific release; this line is the standing rule they all follow.
